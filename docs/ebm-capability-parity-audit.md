# Phase 1 — RRA EBM capability parity audit

Audit date: 2026-10-25  
Branch: `codex/central-taxpayer-workspace`  
Reference implementation: RRA EBM 2.1 computer/tablet manual. The manual is not treated as a specification for Android EBM, Online EBM, or VSDC.

## Official sources reviewed

- [RRA EBM 2.1 computer/tablet user manual (PDF)](https://www.rra.gov.rw/fileadmin/user_upload/EBM2.1_MANUAL_for_compute_and_tablet__english_version.pdf)

## Audit method and boundaries

Reviewed the persisted Drizzle schema and migrations, server actions/services, route handlers, role guards, and trader/admin pages for products, stock, sales, purchases, imports, tax, production, reporting, and audit records. A capability is not considered complete solely because its page or control exists. The RRA manual documents features for its computer/tablet client; it does not establish TaxFlow's approval, legal status, fiscal-device behavior, or the technical API requirements for a VSDC connection.

**Classification legend:** Fully implemented and verified; Partially implemented; UI only; Backend only; Not implemented; Not applicable; Requires external RRA integration or certification.

## Audit summary

- TaxFlow already persists and protects core workflows: role-guarded authentication, buyer TIN lookup for platform businesses, server-side VAT calculation, pending buyer confirmation, transactional stock/VAT updates, imports with review, manufacturer batches, inventory movements, disputes/reversals, reports, and audit history.
- The most direct in-scope gap completed here is reusable customer management for retailer consumer sales. B2B platform buyers remain in the existing taxpayer/user directory; the customer table is not a parallel identity registry for them.
- Product master fields required by the computer/tablet manual are incomplete. Adding tax classifications/rates without an approved, current source would risk financial miscalculation, so they were not guessed.
- TaxFlow does not produce a verified RRA fiscal invoice and must not claim to replace a certified EBM. EBM/VSDC connection remains external and unimplemented.
- This audit does not assert parity for Android EBM, Online EBM, or VSDC based on the computer/tablet manual.

## Implemented in this phase

- Owner-scoped customer directory with create, edit, reversible deactivation/reactivation, optional 9-digit TIN/contact data, server validation, and transactional audit entries.
- Retail sales can select an active saved customer. Server verifies ownership and active status, stores the transaction's customer foreign key, and snapshots the customer name. One-time walk-in sales remain supported.
- The customer UI states that saved TINs are not validated against RRA.

## Verification performed

- Customer schema tests: **4 passed, 0 failed**.
- Full unit suite: **78 passed, 3 failed, 2 skipped**. Failures are in existing `ai-evaluation.test.ts` (tool allowlist) and `rra-rbac.test.ts` (two permission/legacy-role expectations); none mention customer code. The skipped cases require a database connection, so no database integration pass is claimed.
- TypeScript project check: **failed with 146 diagnostics** in existing unrelated files. No diagnostic matched the files changed for this phase.
- ESLint on changed files: **one existing React hooks error** (`set-state-in-effect`) in `components/dashboard/record-sale/record-sale-form.tsx`, plus two existing unused-import warnings (`formatRWF` in that component and `RefreshCw` in sidebar config). The new customer files and customer action/schema passed without diagnostics.
- Production build: **passed with Webpack**. Next reports “Skipping validation of types” because the repository config sets `typescript.ignoreBuildErrors`; this is not a type-check pass. The environment emitted expected missing `BETTER_AUTH_SECRET` and auth base URL warnings during static generation.
- Mobile visual QA and live database migration were not run. The customer form uses responsive grid/list styling but still needs device QA.

The new customer flow requires migration `0017_customer_directory.sql` before it can run against a database. The migration was not applied to a live database.

## External integration/certification prerequisites

Do not advertise TaxFlow as an approved EBM or fiscal-invoicing replacement until RRA confirms the applicable solution and authorizes the integration. Required discovery includes the current VSDC/API specification, authentication and signing requirements, fiscal sequence/reference rules, certification test process, sandbox access, retry/idempotency behavior, and production credentials. This was not performed or simulated in this phase.

## Phase 2 research queue — hypotheses only, not findings

These are questions for evidence gathering, not claims that EBM has the stated limitation:

1. How do each of the four EBM variants behave during network outages, and how are queued invoices reconciled?
2. What are the current official rules and workflows for returns, refunds, correction invoices, and cancellation after release?
3. How are branch, terminal, and multi-location stock records represented and authorized?
4. What backup/restore, device failure, and business-continuity procedures are provided for each variant?
5. Which current product identifiers, tax classifications, rate changes, and unit/package constraints does RRA require?
6. Which evidence or reports expose the relation between opening stock, receipts, sales, losses, and closing stock?

Each question requires current official documentation or observed evidence before proposing a TaxFlow change.
